Perfume-Chem Completion Roadmap
Branch-specific plan for Sol 5.6 Extra High
1. Final product vision
Perfume-Chem should become:

A local-first perfumery operating system that knows what materials are owned, what is physically inside every bottle, what evidence supports each scientific claim, what interventions are possible, how the perfume changes over time, and how the user’s nose responds through repeated experiments.

The final system should combine six capabilities:

Laboratory ledger
Exact formulas, stocks, bottles, measurements, additions, removals, transfers, and maturation history.
Scientific calculation core
Deterministic mass balance, concentration, physical mixture state, OAV screening, safety checks, and uncertainty.
Evidence system
Every property and recommendation linked to its source, authority, scope, and uncertainty.
Intervention engine
Diagnose problems, simulate repairs, compare candidates, and preserve the perfume’s intended identity.
Personal experimental model
Learn from actual bottles, wear tests, preferences, and prediction errors.
Conversational interface
Translate natural language into deterministic operations and explain the results without inventing chemistry.
The language model should be the interpreter and narrator. The workbench should remain the scientific authority.

2. Current branch baseline
The branch has already completed several important foundations:

the engine is packaged as perfume-chem-engine,
the backend depends on that package,
the canonical formula endpoint uses PerfumeWorkbench,
the workbench produces evidence-labeled formula analysis,
exact one-stock bottle addition arithmetic exists,
pipette rounding, staging, and uncertainty are implemented,
unsupported longevity, sillage, and receptor outputs are withheld,
speculative receptor scoring is removed from production simulation.
However, PerfumeWorkbench currently exposes only:

analyze(...)
calculate_addition(...)
Diagnosis, intervention simulation, candidate generation, persistent observations, and comparison workflows remain absent.

The backend also still exposes independent AI, optimizer, mixer, knowledge, feedback, and enhancement routers, so the application has not fully converged on one authority.

The current CI workflow tests only the backend and targets main and develop, while the repository and active PR use master. Root engine tests, data audits, scientific checks, and formula regression fixtures are not enforced by that workflow.

The roadmap must therefore finish the migration around the new truth core.

3. How Sol 5.6 Extra High should operate
Do not give Sol one giant instruction to complete the repository. Each phase should become a sequence of narrow, reviewable pull requests.

For every substantial change, run Sol in four separate passes.

Pass A: Architect
Sol reads the current code, maps call sites, defines the contract, identifies risks, and writes acceptance tests. It does not implement the feature yet.

Pass B: Builder
A fresh Sol session implements only the accepted specification. It must avoid unrelated cleanup.

Pass C: Adversarial reviewer
Another fresh session attempts to disprove the implementation by looking for:

unit confusion,
broken mass conservation,
hidden defaults,
duplicate calculation paths,
invalid migrations,
unsupported scientific claims,
incorrect uncertainty propagation,
security problems,
missing edge cases,
silent changes to old behavior.
Pass D: Repair and verification
A final session fixes confirmed defects and produces the verification report.

10. Phase 6: Build a solvent-inclusive
MixtureState
Goal
Repair the largest remaining physical-model limitation.

The current canonical model explicitly omits the finished ethanol-water-solvent matrix from liquid-phase mole fractions. It also retains density and molecular-weight fallbacks.

New state
MixtureState(
    aromatic_components=...,
    solvent_components=...,
    total_mass=...,
    total_volume=...,
    finished_concentration=...,
    temperature=...,
    humidity=...,
    substrate=...,
    application_mass=...,
    surface_area=...,
    elapsed_time=...,
)
Model tiers
Tier 0: exact bookkeeping
Mass, volume, stock fraction, active material, and composition.

Tier 1: ideal-mixture estimate
Solvent-inclusive composition and measured vapor pressures.

Tier 2: evidence-supported non-ideality
Activity coefficients only when the necessary interaction data exists.

Tier 3: empirically calibrated prediction
Adjustment based on measured headspace, blotter, skin, or user-observation datasets.

Rules
no silent molecular-weight default,
no silent density default,
no activity coefficient without evidence classification,
no universal skin absorption constant,
no false precision,
changing concentration must alter the physical prediction,
changing ethanol, water, DPG, TEC, or IPM must alter the state.
Completion gate
The same concentrate at 10%, 20%, and 30% finished concentration produces meaningfully different and scientifically explainable predictions.

21. Features to avoid until evidence exists
Do not spend major effort on:

universal mood prediction,
universal attractiveness scores,
receptor visualizations based on odor families,
biochemical claims from perfume composition,
unvalidated luxury scores,
enormous embedding infrastructure,
autonomous formula generation without briefs and constraints,
black-box optimization that cannot explain tradeoffs.
These features create impressive screens while weakening scientific credibility.

22. Final definition of completion
Perfume-Chem is complete when:

The complete test and audit suite runs in CI on the real default branch.
There are no unexplained failing tests.
Every interface uses PerfumeWorkbench.
Units are explicit and dimensionally enforced.
Formula versions are immutable.
Stocks represent actual supplier products and dilutions.
Bottles have persistent, auditable event histories.
Every intervention proves mass balance.
Inventory changes follow physical bottle operations.
Scientific values expose provenance and uncertainty.
Strict mode refuses unsupported inputs.
Finished solvent composition affects physical predictions.
Temporal outputs state their validated context.
Receptor hypotheses cannot affect production scoring.
Safety checks are versioned and reproducible.
Intervention candidates preserve the perfume brief.
Recommendations are inventory-aware and pipette-feasible.
Every prediction is stored before the corresponding experiment.
Personalization is evaluated on held-out data.
Chat only invokes and explains deterministic tools.
Every assistant number is traceable.
The complete bottle workflow works through the interface.
The application operates locally without a paid AI provider.
Data can be backed up, restored, migrated, and exported.
A failed upgrade cannot destroy laboratory history.
Unsupported claims are displayed as unknown rather than guessed.
The system can explain both its answer and its limitations.
The product demonstrably improves its predictions through real experiments.
At that point, Perfume-Chem will no longer be a collection of advanced perfume-analysis modules. It will be a coherent scientific instrument: part formulation system, part laboratory notebook, part bottle ledger, part evidence engine, part experimental platform, and part personalized perfumer.
